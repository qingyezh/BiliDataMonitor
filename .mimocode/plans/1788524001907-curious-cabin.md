# 修复：相邻数据点间隔过短问题

## 问题分析

用户报告图表中出现只间隔几秒的数据点，正常应间隔约5分钟。经分析，发现 **3个Bug**，其中2个直接导致此问题：

---

### Bug 1（核心原因）：失败任务不设置 `next_run_at`，导致立即重复执行

**文件**: `src/server/scheduler.ts:119`

```typescript
// 所有重试都失败
const msg = lastError?.message || '未知错误'
markTaskRun(task.id, 'error', msg)  // ← 没有传递 next_run_at！
```

当任务执行失败（网络错误等），`markTaskRun` 被调用时 `nextRunAt` 参数为 `null`。查看 `markTaskRun`（database.ts:243-248）：

```typescript
UPDATE monitor_tasks SET ... next_run_at = COALESCE(?, next_run_at) WHERE id = ?
```

`COALESCE(null, next_run_at)` 会保留旧值，但如果 `next_run_at` 从未被设置过（初始为 null），它就保持 null。

下次心跳检查（scheduler.ts:58）：
```typescript
if (taskRow?.next_run_at && Date.now() < taskRow.next_run_at)
```

`next_run_at` 为 null → 条件为 false → **任务立即再次执行**，不等待间隔。

**影响**：如果一个任务在某轮轮询中失败（比如 B站 API 返回错误），它会在 1 秒后的心跳中立即重试，而不是等待间隔时间。如果连续失败，就会产生密集的执行记录。

---

### Bug 2：`up_daily_stats` 的 delta 计算永远返回 0

**文件**: `src/server/database.ts:384-386`

```typescript
const dateStr = new Date(now).toISOString().slice(0, 10)  // "2026-09-04" (字符串)
const prev = d.prepare('SELECT ... FROM up_history WHERE mid = ? AND created_at < ? ...')
    .get(mid, dateStr)  // created_at 是毫秒时间戳，dateStr 是字符串
```

`created_at` 存储的是毫秒时间戳（如 `1725456000000`），而 `dateStr` 是 `"2026-09-04"` 格式的字符串。SQLite 中 `"2026-09-04" < 1725456000000` 总为 true（字符串转数字后远小于时间戳），所以 `prev` 查询 **永远返回 undefined**，导致 `delta_views` 等始终为 0。

---

### Bug 3：`video_history` 缺少防过密刷新机制

`up_history` 有 240 秒防过密逻辑（database.ts:541-559），但 `video_history` 的写入（`writeUpSnapshot` 和 `writeVideoSnapshot`）没有类似保护。如果 API 返回略有不同的数据（B站播放数缓存波动），每次都会插入新记录。

---

## 修复方案

### 修复 1：失败任务也设置 `next_run_at`

**文件**: `src/server/scheduler.ts:119`

```typescript
// 修改前
markTaskRun(task.id, 'error', msg)

// 修改后
markTaskRun(task.id, 'error', msg, now + intervalMs)
```

需要将 `now` 变量的作用域提升到 for 循环外部，以便在失败分支也能使用。

### 修复 2：修正 `up_daily_stats` 的 delta 查询

**文件**: `src/server/database.ts:384-386`

```typescript
// 修改前：dateStr 是字符串，与 created_at (毫秒时间戳) 类型不匹配
const dateStr = new Date(now).toISOString().slice(0, 10)
const prev = d.prepare('... created_at < ? ...').get(mid, dateStr)

// 修改后：使用毫秒时间戳计算当天起始时间
const todayStart = new Date(now)
todayStart.setHours(0, 0, 0, 0)
const todayStartMs = todayStart.getTime()
const prev = d.prepare('... created_at < ? ...').get(mid, todayStartMs)
```

这样就能正确找到"今天之前"的最后一条 up_history 记录。

### 修复 3：为 `video_history` 添加防过密机制

在 `writeUpSnapshot` 和 `writeVideoSnapshot` 中，写入 `video_history` 前检查最近一条记录的时间间隔和值是否相同，若间隔 < 60秒 且值相同则跳过。

**文件**: `src/server/database.ts` — `writeUpSnapshot` 函数（第287-301行区域）

在 `insHist.run(...)` 之前增加检查：

```typescript
// 检查最近一条 video_history 是否间隔太短且值相同
const lastHist = d.prepare(
  'SELECT play, video_review, comment, duration, created_at FROM video_history WHERE bvid = ? ORDER BY created_at DESC LIMIT 1'
).get(v.bvid) as { play: number; video_review: number; comment: number; duration: number; created_at: number } | undefined
const tooClose = lastHist && (now - lastHist.created_at < 60_000) &&
  lastHist.play === v.play && lastHist.video_review === v.video_review &&
  lastHist.comment === v.comment && lastHist.duration === v.duration
if (!tooClose) {
  insHist.run(v.bvid, v.play, v.video_review, v.comment, v.duration, now)
  changed++
}
```

同理对 `writeVideoSnapshot` 做相同处理。

## 验证方式

1. `pnpm build`（在 src/server 目录）确保编译通过
2. 启动后端 `node --experimental-sqlite src/server/dist/index.js`
3. 观察日志：失败任务后是否不再立即重试
4. 查看 `video_history` 表：确认不存在间隔 < 60秒 的重复记录
5. 查看 `up_daily_stats` 表：确认 `delta_views` 不再全为 0
